# التحويل إلى Redis — دليل المشغّل

**الحالة:** التطبيق **جاهز** لـ Redis من ناحية الكود. لا يحتاج أي حزمة
إضافية ولا أي تغيير برمجي — فقط تثبيت على الخادم وثلاثة أسطر في `.env`.

---

## هل تحتاجه أصلاً؟

اليوم تعمل الجلسات والذاكرة المؤقتة وطابور المهام على **قاعدة البيانات**.
هذا خيار سليم ويعمل. لكنه يدفع ثمناً: كل نقرة موظّف تكتب في الجلسة، وكل
مهمة خلفية تكتب وتقرأ من نفس الجدول الذي يخدم الزبائن.

> **القاعدة العملية:** ما دام الفريق أقلّ من ٥–١٠ أشخاص والصفحات سريعة،
> فقاعدة البيانات كافية تماماً. الانتقال إلى Redis يستحقّ حين تلاحظ بطئاً
> عاماً، أو حين يعمل أكثر من عامل طابور واحد.

لا تحوّل لأن Redis «أفضل نظرياً». حوّل حين ترى سبباً.

---

## الخطوات على الخادم

**١. التثبيت** (خادم Ubuntu/Debian):

```
sudo apt update
sudo apt install redis-server php8.3-redis
```

**٢. تأكّد أن الخدمة تعمل:**

```
systemctl status redis-server
redis-cli ping
```

يجب أن يردّ `PONG`. إن لم يردّ، لا تُكمل.

**٣. تأكّد أن PHP يرى الإضافة:**

```
php -m | grep redis
```

يجب أن يظهر `redis`. إن لم يظهر، أعد تشغيل PHP:

```
sudo systemctl restart php8.3-fpm
```

## الأمان — لا تتجاوز هذه

Redis افتراضياً **بلا كلمة سر** ويستمع على `127.0.0.1` فقط. هذا مقبول ما
دام على نفس الخادم. تحقّق:

```
grep -E "^bind|^requirepass|^protected-mode" /etc/redis/redis.conf
```

> ⚠️ **إن كان `bind` يسمح باتصالات خارجية، أوقف كل شيء وأصلحه أولاً.**
> Redis مكشوف على الإنترنت بلا كلمة سر يعني تسليم جلسات كل موظفيك وزبائنك.

للأمان الإضافي، اضبط كلمة سر في `redis.conf`:

```
requirepass <كلمة-سر-طويلة-عشوائية>
```

ثم أضفها في `.env` كـ `REDIS_PASSWORD` (لا تضعها في المستودع أبداً).

---

## التحويل في `.env`

على الخادم في `/var/www/dienstly24/portal/.env`:

```
REDIS_CLIENT=phpredis
REDIS_HOST=127.0.0.1
REDIS_PORT=6379
REDIS_PASSWORD=null

SESSION_DRIVER=redis
CACHE_STORE=redis
QUEUE_CONNECTION=redis
```

ثم:

```
php artisan config:clear
php artisan config:cache
```

## ⚠️ نقطتان قبل أن تحوّل الطابور

**١. المهام المنتظرة حالياً في قاعدة البيانات لن تنتقل.** أفرغ الطابور
أولاً — تأكّد أن جدول `jobs` فارغ قبل التحويل:

```
php artisan queue:work --stop-when-empty
```

**٢. أعد تشغيل عامل الطابور بعد التحويل**، وإلا بقي يستمع على الطابور
القديم:

```
sudo systemctl restart <اسم-خدمة-العامل>
```

كذلك تحويل الجلسات سيُخرج **كل** المستخدمين المسجَّلين حالياً. هذا غير
ضارّ، لكن اختر وقتاً هادئاً.

**٣. عامل ثانٍ للمهام الطويلة** (تدقيق ١٥.٠٩.٢٠٢٦). استيراد العملاء
(`ImportCustomersJob`) قد يستغرق حتى ٣٠ دقيقة، ولذلك يعمل على اتصال
خاص (`redis-lang`، طابور `lang`) لا على الطابور العادي. يحتاج عاملاً
منفصلاً:

```
php artisan queue:work redis --queue=default --sleep=3 --tries=3 --max-time=3600
php artisan queue:work redis-lang --queue=lang --sleep=5 --tries=1 --timeout=1800 --max-time=3600
```

انتبه إلى `--queue=default` في العامل الأول: بدونها سيلتقط المهام
الطويلة أيضاً ويعالجها بمهلة الطابور القصيرة — وهو بالضبط ما يتجنّبه
هذا الفصل. إذا لم يعمل العامل الثاني، يبقى الاستيراد منتظراً — لا
يُفقد ولا يُنفَّذ مرتين.

> **ما كان سيحدث بدون هذا التدقيق:** الإعداد الافتراضي لـ Redis في
> Laravel هو `retry_after = 90` ثانية، بينما سبع مهام لدينا تستغرق
> حتى ٣٠٠ ثانية — منها نشر المنشورات على إنستغرام وإرسال الحملات
> البريدية. كان التحويل إلى Redis سيعيد سحب كل واحدة منها بعد ٩٠ ثانية
> بينما ما تزال تعمل: **منشور مكرّر على إنستغرام، وحملة بريدية مُرسَلة
> مرتين.** رُفعت القيمة الآن إلى ٣٦٠ ثانية، ويوجد اختبار حارس
> (`QueueTimeoutTest`) يمنع رجوع المشكلة — ويفحص Redis وقاعدة البيانات
> معاً.

## التحقّق من النجاح

افتح **`/admin/systemzustand`** ← قسم «الخدمات الخارجية» ← السطر
**«Sitzungen / Cache / Warteschlange»**.

| ما تراه | المعنى |
|---|---|
| 🟢 `... Redis erreichbar` | نجح التحويل فعلاً |
| 🔴 `Redis NICHT erreichbar` | الإعداد مضبوط لكن Redis لا يردّ — راجع الخطوة ٢ |
| ⚪ يذكر `database` | لم يُطبَّق التغيير — على الأغلب نسيت `config:cache` |

الصفحة تُجري **اتصال PING حقيقياً**، فالسطر الأخضر دليل، لا تخمين.

---

## التراجع

إن ساء شيء، أعِد الأسطر الثلاثة في `.env` إلى:

```
SESSION_DRIVER=database
CACHE_STORE=database
QUEUE_CONNECTION=database
```

ثم `php artisan config:cache` وأعد تشغيل عامل الطابور. لا شيء يُفقد —
البنية جاهزة للاثنين.
